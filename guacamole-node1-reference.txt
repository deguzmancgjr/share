OUTCOME ON node2
----------------
PC 10.2.228.134 successfully reached:
  https://10.2.229.50/guacamole/

Root cause of the original failure:
  VM 108 had TWO default routes:
    default via 10.100.0.1 dev ens18          (metric 0, lab)
    default via 10.2.229.1 dev ens19 metric 100 (mgmt)
  Linux preferred the lab default. Replies to 10.2.228.134 therefore
  left via 10.100.0.1 with source 10.100.0.50, so the PC never got a
  valid reply. The server saw the request, but the return path was wrong
  (asymmetric routing).

Fix:
  Add a specific route for the client subnet via the MANAGEMENT gateway:
    10.2.228.0/24 via 10.2.229.1 dev ens19
  A longer-prefix route beats the default route, so replies now leave
  with source 10.2.229.50. Persist it in netplan.

Verified after the fix:
  - tcpdump: bidirectional TLS packets 10.2.228.134 <-> 10.2.229.50:443
  - Caddy log: remote_ip 10.2.228.134
  - Guacamole session API: HTTP 204
  - Browser: Edge loaded Guacamole successfully

=====================================================================
2. THE ACTUAL FIX - ADD A RETURN ROUTE FOR THE CLIENT SUBNET
=====================================================================

2.1 Diagnose first
------------------
Inside the Guacamole VM:

  ip route get <CLIENT_IP>

BAD (node2 before the fix):
  10.2.228.134 via 10.100.0.1 dev ens18 src 10.100.0.50

GOOD (after the fix):
  10.2.228.134 via 10.2.229.1 dev ens19 src 10.2.229.50

Meaning:
  - If it goes via the lab default, replies use the lab source IP and
    the client usually drops them. This looks exactly like "cannot
    access" even though the request arrived.
  - The specific route must point at the MANAGEMENT gateway and the
    management interface.

2.2 Apply immediately (temporary, no reboot required)
-----------------------------------------------------

  ip route replace <CLIENT_SUBNET> via <MGMT_GW> dev <MGMT_IF>

Example (node2):
  ip route replace 10.2.228.0/24 via 10.2.229.1 dev ens19

Verify:
  ip route get <CLIENT_IP>
  ip route get <DNS1>

2.3 Persist in netplan
----------------------
Edit the netplan file that defines the management NIC. On node2 it was
/etc/netplan/50-cloud-init.yaml (it was originally cloud-init generated,
but it had already been customized).

Add the client subnet (and the campus DNS subnet, if DNS is reached via
the management gateway) under the mgmt stanza routes.

Full node2 example:

network:
  version: 2
  renderer: networkd
  ethernets:
    lab:
      match:
        macaddress: "bc:24:11:a5:3e:82"
      dhcp4: false
      addresses:
        - 10.100.0.50/24
      routes:
        - to: default
          via: 10.100.0.1
      optional: true

    mgmt:
      match:
        macaddress: "bc:24:11:63:39:26"
      dhcp4: false
      dhcp6: false
      accept-ra: false
      addresses:
        - 10.2.229.50/24
      routes:
        - to: default
          via: 10.2.229.1
          metric: 100
        - to: 10.2.228.0/24
          via: 10.2.229.1
        - to: 10.2.196.0/24
          via: 10.2.229.1
      nameservers:
        addresses: [10.2.196.11, 10.2.196.12]
        search: [ad.phl-imcite.net]

Notes:
  - Leave the lab default route as-is; it is used for lab and internet
    traffic. The specific /24 route wins over the default.
  - Do NOT set a metric on the specific route; prefix length decides.
  - If your clients are on 10.2.228.0/24, use exactly that. If they are
    on another subnet, replace it.
  - If DNS is on the same campus range, add 10.2.196.0/24 too, or a
    suitable summary route.

2.4 Back up, validate, apply
----------------------------

  cp -a /etc/netplan/50-cloud-init.yaml \
        /root/50-cloud-init.yaml.bak-$(date +%F-%H%M%S)

  chmod 600 /etc/netplan/50-cloud-init.yaml
  netplan generate
  netplan apply

Verify again:
  ip route get <CLIENT_IP>
  ip route get <DNS1>
  ip route

2.5 Optional: stop cloud-init overwriting the file
--------------------------------------------------
If the file is managed by cloud-init, add:

  tee /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg >/dev/null <<'EOF'
  network: {config: disabled}
  EOF

This disables cloud-init's network configuration only. The manual
netplan file remains authoritative.

2.6 If you get locked out
-------------------------
The Proxmox console still works. Restore the backup:

  cp -a /root/50-cloud-init.yaml.bak-YYYY-MM-DD-HHMMSS \
        /etc/netplan/50-cloud-init.yaml
  netplan apply

Or use the QEMU guest agent from the node:

  qm guest exec <VMID> -- bash -c 'cp -a /root/50-cloud-init.yaml.bak-* /etc/netplan/50-cloud-init.yaml && netplan apply'

=====================================================================
4. GUACAMOLE DOCKER STACK
=====================================================================

The working node2 stack is three services:
  - guacd      (remote desktop proxy)
  - mysql      (Guacamole database)
  - guacamole  (Tomcat web app)

Key points:
  - All three must be on the SAME Docker network, otherwise the web app
    cannot resolve guacd. On node2 guacd had been left on the default
    network while the web app was on guacamole-net; this was corrected.
  - The web app must NOT publish 8080 to the world. Bind it to
    127.0.0.1 only; Caddy is the only exposed service.
  - Caddy uses host networking so it sees the REAL client IP. If Caddy
    runs bridged, remote_ip can become the Docker gateway and the IP
    allowlist breaks.

`<GUAC_DIR>/docker-compose.yml` (node2 working version):

services:
  guacd:
    image: guacamole/guacd:latest
    container_name: guacd
    restart: unless-stopped
    networks:
      - guacamole-net

  mysql:
    image: mysql:8.0
    container_name: guacamole_mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: <DB_ROOT_PASSWORD>
      MYSQL_DATABASE: guacamole_db
      MYSQL_USER: guacuser
      MYSQL_PASSWORD: <DB_GUAC_PASSWORD>
    volumes:
      - ./data/mysql:/var/lib/mysql
      - ./init:/docker-entrypoint-initdb.d
    networks:
      - guacamole-net

  guacamole:
    image: guacamole/guacamole:latest
    container_name: guacamole
    restart: unless-stopped
    ports:
      - "127.0.0.1:8080:8080"
    environment:
      GUACD_HOSTNAME: guacd
      MYSQL_HOSTNAME: mysql
      MYSQL_DATABASE: guacamole_db
      MYSQL_USER: guacuser
      MYSQL_PASSWORD: <DB_GUAC_PASSWORD>
      MYSQL_ENABLED: "true"
    depends_on:
      - guacd
      - mysql
    networks:
      - guacamole-net

  caddy:
    image: caddy:2
    container_name: guacamole_caddy
    restart: unless-stopped
    network_mode: host
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - ./certs:/etc/caddy/certs:ro
    depends_on:
      - guacamole

networks:
  guacamole-net:
    driver: bridge

Notes:
  - Replace <DB_ROOT_PASSWORD> and <DB_GUAC_PASSWORD> with strong unique
    values on a fresh node1 deployment. If node1 already has a populated
    DB volume, changing these values requires rotating the DB credentials
    safely; otherwise keep the existing values.
  - The `./init` directory must contain the Guacamole JDBC schema
    (initdb.sql) for a fresh database. If node1 is already initialized,
    keep its existing init/data directories.
  - The official Guacamole image loads the MySQL auth and brute-force
    ban extensions when MYSQL_ENABLED=true. TOTP is not enabled by
    default (see hardening section).

Apply:

  cd <GUAC_DIR>
  docker compose config --quiet
  docker compose up -d
  docker compose ps

Expected:
  guacamole       Up   127.0.0.1:8080->8080/tcp
  guacamole_caddy Up
  guacamole_mysql Up
  guacd           Up

Verify guacd is on the same network as the web app:

  docker exec guacamole getent hosts guacd
  # must return a 172.x address

  docker logs guacd --tail 10
  # must show: Listening on host 0.0.0.0, port 4822


=====================================================================
5. TLS REVERSE PROXY WITH CADDY
=====================================================================

Why Caddy:
  - Simple TLS termination.
  - Built-in IP allowlist (remote_ip).
  - Host networking gives the real client IP.
  - Handles WebSockets automatically (Guacamole needs this).

5.1 Create the certificate (self-signed, IP + DNS SANs)
-------------------------------------------------------

  cd <GUAC_DIR>
  mkdir -p certs

  openssl req -x509 -nodes -newkey rsa:4096 -sha256 -days 825 \
    -keyout certs/guac.key \
    -out certs/guac.crt \
    -subj "/CN=<MGMT_IP>" \
    -addext "subjectAltName=IP:<MGMT_IP>,DNS:<GUAC_HOSTNAME>"

  chmod 600 certs/guac.key

  openssl x509 -in certs/guac.crt -noout \
    -subject -issuer -dates -ext subjectAltName

Node2 result:
  subject=CN = 10.2.229.50
  SAN: IP Address:10.2.229.50, DNS:guac.ad.phl-imcite.net
  valid: 2026-10-21 -> 2029-01-23

5.2 Caddyfile
-------------

`<GUAC_DIR>/Caddyfile`:

:443 {
	tls /etc/caddy/certs/guac.crt /etc/caddy/certs/guac.key

	@denied not remote_ip <CLIENT_SUBNET> <MGMT_SUBNET>
	respond @denied "Forbidden" 403

	@root path /
	redir @root /guacamole/ 302

	header {
		X-Content-Type-Options "nosniff"
		X-Frame-Options "SAMEORIGIN"
		Referrer-Policy "no-referrer"
	}

	reverse_proxy 127.0.0.1:8080

	log {
		output stdout
		format console
	}
}

Replace:
  <CLIENT_SUBNET>  e.g. 10.2.228.0/24
  <MGMT_SUBNET>    e.g. 10.2.229.0/24

Why include the management subnet? It lets you test from the Proxmox
node (e.g. curl from 10.2.229.10) without weakening access to your PC
subnet. Remove it if you do not want that.

5.3 Start / reload
------------------

  cd <GUAC_DIR>
  docker compose up -d caddy

  # If Caddy is already running and only the Caddyfile changed:
  docker exec guacamole_caddy caddy reload --config /etc/caddy/Caddyfile

  docker logs guacamole_caddy --tail 30

Expected:
  server running ... :443
  serving initial configuration
  (a warning about HTTP/2 on :80 is harmless; :80 is used for redirect)


=====================================================================
6. UFW RULES (IMPORTANT WITH HOST-MODE CADDY)
=====================================================================

Docker-published ports can bypass UFW because Docker inserts its own
iptables rules. That is why the original 8080 was reachable even though
UFW only allowed 22.

We changed the design:
  - 8080 is bound to 127.0.0.1, so Docker does not publish it.
  - Caddy runs with network_mode: host, so UFW DOES apply to 443/80.

Inside the VM:

  ufw allow from <CLIENT_SUBNET> to any port 443 proto tcp
  ufw allow from <MGMT_SUBNET>   to any port 443 proto tcp
  ufw allow from <CLIENT_SUBNET> to any port 80  proto tcp
  ufw allow from <MGMT_SUBNET>   to any port 80  proto tcp

  ufw status numbered

Node2 final rules:
  [1] 22/tcp   ALLOW IN  Anywhere
  [2] 443/tcp  ALLOW IN  10.2.228.0/24
  [3] 443/tcp  ALLOW IN  10.2.229.0/24
  [4] 80/tcp   ALLOW IN  10.2.228.0/24
  [5] 80/tcp   ALLOW IN  10.2.229.0/24
  [6] 22/tcp (v6) ALLOW IN Anywhere (v6)

Port 80 is optional: it only provides an HTTP -> HTTPS redirect so users
who type the bare IP still land on HTTPS.

=====================================================================
8. TROUBLESHOOTING DECISION TREE
=====================================================================

8.1 Browser times out, no packets arrive
----------------------------------------
Check on the VM:

  tcpdump -ni any host <CLIENT_IP> and port 443

Then retry from the PC.

  - No packets at all:
      upstream campus ACL/firewall, wrong IP, browser proxy, or the PC
      is not actually using the source IP you think.

  - SYN arrives, no SYN-ACK:
      return path / asymmetric routing. Run:
        ip route get <CLIENT_IP>
      It must use <MGMT_GW>/<MGMT_IF> and source <MGMT_IP>.
      If it uses the lab gateway, repeat Section 2.

  - TLS handshake happens but browser errors:
      certificate trust/SAN problem (Section 9).

  - Packets arrive and responses leave, but the PC still fails:
      campus firewall may allow outbound but drop return traffic; check
      with the network team. A successful tcpdump on the VM with a failed
      PC is usually upstream filtering or a local PC proxy.

8.2 HTTP 403 Forbidden
----------------------
The client IP is not in the Caddy allowlist.

  - Confirm the PC's real source IP in the Caddy log:
      docker logs guacamole_caddy --tail 50 | grep <CLIENT_IP>
  - Update @denied in the Caddyfile with the correct <CLIENT_SUBNET>.
  - Reload:
      docker exec guacamole_caddy caddy reload --config /etc/caddy/Caddyfile

8.3 HTTP 502 Bad Gateway / blank page
-------------------------------------
Caddy is up but the web app is not reachable.

  cd <GUAC_DIR>
  docker compose ps
  docker logs guacamole --tail 50
  curl -sI http://127.0.0.1:8080/guacamole/

If 8080 works locally but 443 gives 502, check the Caddy reverse_proxy
target (127.0.0.1:8080 with host networking).

8.4 Login page loads, but connections fail
------------------------------------------
guacd is not reachable or the target guest is down.

  docker exec guacamole getent hosts guacd
  docker logs guacd --tail 30
  docker logs guacamole --tail 50

Verify the target VM IP/port from the Guacamole VM:

  nc -vz <TARGET_IP> 3389     # Windows RDP
  nc -vz <TARGET_IP> 5900     # VNC
  nc -vz <TARGET_IP> 22       # SSH

Also confirm the Guacamole VM's lab routing to 10.5.0.x, 10.7.0.x,
10.100.0.x, etc. The node2 VM used 10.100.0.1 as the lab default gateway.

8.5 Old :8080 URL no longer works
---------------------------------
Expected. 8080 is now 127.0.0.1-only. Use:
  https://<MGMT_IP>/guacamole/

8.6 Docker network warning
--------------------------
If guacd and guacamole are on different Docker networks, the web app
cannot resolve `guacd`. Ensure all services have:

  networks:
    - guacamole-net

Verify:
  docker inspect guacd --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
  docker inspect guacamole --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'

=====================================================================
11. SECURITY HARDENING (RECOMMENDED AFTER ACCESS WORKS)
=====================================================================

11.1 Enable TOTP (MFA)
----------------------
Add to the guacamole service environment in docker-compose.yml:

      TOTP_ENABLED: "true"
      TOTP_ISSUER: "CTRDC Lab"

Then:
  docker compose up -d guacamole

Users enroll an authenticator app on their next login. Test with one
account before rolling it out to everyone. Keep a way to disable it
(remove the variables and recreate the container) in case of lockout.

11.2 Restrict SSH
-----------------
Node2 currently allows 22 from anywhere. Restrict it to management and
client subnets. Keep the Proxmox console available before doing this:

  ufw delete allow 22/tcp
  ufw allow from <MGMT_SUBNET> to any port 22 proto tcp
  ufw allow from <CLIENT_SUBNET> to any port 22 proto tcp
  ufw status numbered

11.3 Replace weak DB credentials
--------------------------------
The node2 compose contains placeholder/weak DB passwords. On a fresh
node1 deployment, use strong unique values. For an existing DB, rotate
the MySQL user password first, then update the compose values, then
recreate the containers.

11.4 Protect the DB dump
------------------------
Guacamole stores connection credentials in MySQL. Treat DB dumps as
secrets; do not put them in shared folders or chat.

11.5 Restrict Proxmox 8006
--------------------------
Do not expose the Proxmox UI publicly. Remove the global 8006 accept in
the cluster firewall and restrict it to management/admin sources.

11.6 Consider fail2ban
----------------------
Guacamole's brute-force "ban" extension is already loaded (5 failed
attempts -> 300 s ban). You can add fail2ban for Caddy/Guacamole logs if
you want longer or custom bans.

13. WHAT CAUSED THE ORIGINAL FAILURE - SHORT VERSION
=====================================================================

Symptom:
  Request reached VM 108 (tcpdump showed it), but the PC still could not
  load Guacamole.

Cause:
  Two default routes. The lab default (10.100.0.1) had metric 0 and won.
  Replies to 10.2.228.134 were sent via the lab NIC with source
  10.100.0.50, so the return traffic was invalid/dropped.

Fix:
  Add a specific route for the client subnet via the mgmt gateway:
    10.2.228.0/24 via 10.2.229.1 dev ens19
  Persist it in netplan under the mgmt interface.

Proof:
  Before: ip route get 10.2.228.134
           -> via 10.100.0.1 dev ens18 src 10.100.0.50
  After:  ip route get 10.2.228.134
           -> via 10.2.229.1 dev ens19 src 10.2.229.50

  tcpdump then showed bidirectional TLS, and Caddy logged:
           remote_ip 10.2.228.134
           POST /guacamole/api/session -> 204
  The Edge browser on the PC loaded the Guacamole UI successfully.
